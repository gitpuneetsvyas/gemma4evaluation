## 3. Data Consistency Strategy for Inventory

Maintaining strict real-time inventory consistency is paramount. We will us[2D[K
use a **Command Query Responsibility Segregation (CQRS)** model combined wi[2D[K
with an **Event Sourcing** pattern for inventory management.

### Strategy: Write-Through and Event Sourcing

1. **Source of Truth (Write Path):** The primary inventory record resides i[1D[K
in a relational database (Aurora PostgreSQL) to guarantee ACID properties ([1D[K
(Atomicity, Consistency, Isolation, Durability).
2. **Real-Time Updates (Write-Through):**
    *   Warehouse updates do not directly modify the inventory view. Instea[6D[K
Instead, they publish an `InventoryUpdate` event to a **Kafka Topic**.
    *   The Inventory Service consumes these events, validates them, and pe[2D[K
performs the transaction on the primary database.
3. **Cache Invalidation (Read Path):**
    *   Immediately after a successful database write, the Inventory Servic[6D[K
Service publishes a `StockUpdated` event.
    *   All relevant cache nodes (Redis) subscribe to these events and use [K
them to **invalidate (delete)** the specific product keys or update the sto[3D[K
stock count in the distributed cache.
4. **Read Consistency (Query):**
    *   When a user requests inventory (a read operation), the system prior[5D[K
prioritizes the **Distributed Cache (Redis)**.
    *   If the cache is missed, the system queries the database (Tier 4). T[1D[K
This ensures *eventual consistency* for reads, which is acceptable for prod[4D[K
product display, while writes are strictly consistent.

This strategy ensures that while the database remains strictly consistent, [K
the high-volume read traffic is served by sub-100ms cache lookups, meeting [K
the performance requirement.
