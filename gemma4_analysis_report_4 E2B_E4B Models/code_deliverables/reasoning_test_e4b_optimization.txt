## 3. Data Consistency Strategy for Inventory (The Hard Problem)

Achieving real-time, strong consistency for inventory under extreme load is[2D[K
is the most challenging requirement. We cannot use simple cache invalidatio[11D[K
invalidation for inventory due to the risk of overselling.

**Pattern Used: Optimistic Locking with a Dedicated Inventory Service (Sour[5D[K
(Source of Truth Cache)**

1.  **Dedicated Inventory Service:** All inventory reads and writes must pa[2D[K
pass through a dedicated, highly optimized microservice.
2.  **Reservation Queue (Tier 5):** When a user adds items to the cart or i[1D[K
initiates checkout, the Inventory Service does *not* write directly to the [K
main DB. Instead, it writes a time-limited **Reservation Request** to the W[1D[K
Write Cache (Redis).
3.  **Atomic Decrement (Strong Consistency):** The actual inventory count d[1D[K
decrement (the write) is performed using an atomic transaction (`DECRBY` in[2D[K
in Redis or a database transaction with a unique transaction ID). This prev[4D[K
prevents multiple users from claiming the last few items simultaneously.
4.  **Asynchronous Stock Update:** After a successful reservation, the Inve[4D[K
Inventory Service publishes an immutable **`InventoryReserved`** event to t[1D[K
the Kafka Stream (Tier 4).
    *   **Consumers:** Downstream services (e.g., Pricing Engine, Catalog S[1D[K
Service, CDN Cache invalidation) subscribe to this stream to update their c[1D[K
caches.
    *   **Failover:** The main PostgreSQL database remains the final Source[6D[K
Source of Truth. The Reservation Queue periodically attempts to reconcile f[1D[K
failed/timed-out reservations back into the DB.
5.  **Read Strategy:** Catalog searches read from the Redis Cache (Tier 3) [K
for *availability hints*, but the final checkout step *must* query the dedi[4D[K
dedicated Inventory Service (which reads the write cache).
