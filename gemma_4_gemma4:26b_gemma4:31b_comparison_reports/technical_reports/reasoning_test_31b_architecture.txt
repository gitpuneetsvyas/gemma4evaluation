# 1. Target Architecture Design

### Microservices Decomposition (Domain-Driven Design)
We will decompose the monolith into bounded contexts. I have identified 25 [K
core services categorized by domain:

**A. Customer & Identity Domain**
1. `Identity-Service`: OAuth2/OIDC, MFA, Session management.
2. `UserProfile-Service`: Profile, preferences, address book.
3. `Notification-Service`: Email, SMS, Push (Async).
4. `Loyalty-Service`: Points, rewards, tiers.

**B. Commerce & Sales Domain**
5. `Catalog-Service`: Product metadata, attributes.
6. `Price-Service`: Dynamic pricing, multi-currency logic.
7. `Cart-Service`: Temporary storage of items (High write/read).
8. `Order-Service`: Order orchestration and lifecycle.
9. `Payment-Service`: Gateway integrations, PCI-DSS vaulting.
10. `Promotion-Service`: Coupons, flash sale logic.
11. `Tax-Service`: Regional tax calculations.

**C. Inventory & Fulfillment Domain**
12. `Inventory-Service`: Real-time stock levels across 10k warehouses.
13. `Warehouse-Service`: Bin location, picking/packing.
14. `Shipping-Service`: Carrier integration, tracking.
15. `Returns-Service`: Reverse logistics.

**D. Seller & Partner Domain**
16. `Seller-Portal-Service`: Onboarding, store management.
17. `Product-Ingestion-Service`: Bulk uploads from sellers.
18. `Settlement-Service`: Seller payouts and invoicing.
19. `Partner-API-Gateway`: External integration layer.

**E. Intelligence & Search Domain**
20. `Search-Service`: Full-text search, filtering (Elasticsearch).
21. `Recommendation-Service`: ML-driven "You may also like."
22. `Personalization-Service`: User-specific landing pages.
23. `Analytics-Service`: Real-time clickstream processing.

**F. Cross-Cutting Domain**
24. `Audit-Service`: Compliance logging (SOX/GDPR).
25. `Currency-Service`: Real-time FX rate updates.

# 3. Migration Strategy (24-Month Timeline)

We will utilize the **Strangler Fig Pattern**, wrapping the monolith in a p[1D[K
proxy and peeling off services one by one.

### Phase 1: Foundation & Core Services (0-6 Months)
*   **Infrastructure:** Setup AWS Landing Zone, EKS Clusters, Kafka Backbon[7D[K
Backbone.
*   **Identity Shift:** Extract `Identity-Service` first. Implement a "Unif[5D[K
"Unified Auth" layer that bridges the monolith and new services.
*   **API Gateway:** Deploy Kong. All traffic still goes to the monolith, b[1D[K
but the Gateway is now the entry point.

### Phase 2: Customer-Facing Services (6-12 Months)
*   **Read-Heavy Services:** Extract `Catalog`, `Search`, and `Cart`.
*   **Data Sync:** Use CDC (Change Data Capture) from Oracle 11g to Kafka t[1D[K
to populate new NoSQL/Search stores.
*   **Traffic Shifting:** Use Istio to route 1% $\rightarrow$ 10% $\rightar[9D[K
$\rightarrow$ 100% of traffic to new services.

### Phase 3: Seller & Inventory Services (12-18 Months)
*   **Critical Writes:** Extract `Order`, `Payment`, and `Inventory`.
*   **Complex Migration:** Implement the **Saga Pattern** to handle distrib[7D[K
distributed transactions across the remaining monolith and new microservice[12D[K
microservices.
*   **Inventory Real-time:** Shift 10k warehouses to the new `Inventory-Ser[14D[K
`Inventory-Service` using a regional sharding strategy.

### Phase 4: Analytics & ML Services (18-24 Months)
*   **Intelligence:** Deploy `Recommendation` and `Personalization` service[7D[K
services.
*   **Data Lake:** Stream all Kafka events into Amazon S3/Snowflake for lon[3D[K
long-term analytics.
*   **Monolith Decommission:** Final shut down of the legacy Java 8 app.

# 4. Implementation Details

### Database Schema: Order Service (PostgreSQL)
```sql
CREATE TABLE orders (
    order_id UUID PRIMARY KEY,
    customer_id UUID NOT NULL,
    total_amount DECIMAL(12,2),
    currency_code VARCHAR(3),
    status VARCHAR(20), -- PENDING, PAID, SHIPPED, CANCELLED
    created_at TIMESTAMP WITH TIME ZONE DEFAULT CURRENT_TIMESTAMP,
    version INT -- For optimistic locking
);

CREATE TABLE order_items (
    item_id UUID PRIMARY KEY,
    order_id UUID REFERENCES orders(order_id),
    product_id UUID NOT NULL,
    quantity INT,
    unit_price DECIMAL(12,2)
);
-- Index for fast lookup by customer
CREATE INDEX idx_orders_customer ON orders(customer_id);
```

# 5. Scalability and Performance

### Handling 50x Traffic Spikes (Flash Sales)
1.  **Predictive Auto-scaling:** Use AWS Predictive Scaling to spin up node[4D[K
nodes *before* the sale starts based on historical patterns.
2.  **Write-Behind Caching:** Use Redis as a buffer for inventory decrement[9D[K
decrements. Queue the actual DB update via Kafka to prevent DB lock content[7D[K
contention.
3.  **Queue-Based Load Leveling:** Use Kafka to buffer incoming orders duri[4D[K
during peaks, protecting the `Order-Service` from crashing.

### Caching Strategy
*   **L1 (CDN):** Static assets and product images (CloudFront).
*   **L2 (Edge):** Global cached responses for top 1,000 products (Lambda@E[9D[K
(Lambda@Edge).
*   **L3 (Distributed):** Redis clusters for session data and inventory.
*   **L4 (Local):** Caffeine cache inside Java services for configuration d[1D[K
data.
